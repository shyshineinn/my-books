# 双数据库架构 · 部署与运维

> calibre 管「书是什么」,`reading.db` 管「我读得怎么样」。
> 前端是新写的现代界面,阅读记录功能完全自持。

---

## 一、架构总览

```
浏览器 https://helloac.top
   │
   ▼ Nginx(443, TLS 终结 / gzip / 安全头)
   ├── /                → Node my-books(127.0.0.1:3002)
   │     ├── /next/*      新前端(书单 / 详情 / 统计)
   │     ├── /api/calibre/*  转发给 calibre,并把 reading.db 的状态 join 进来
   │     ├── /api/reading/*  阅读记录读写(自有库)
   │     └── /api/notes、/api/img-proxy  出站代理(与 calibre 无关,保留)
   │
   └── /calibre/*       → calibre-server(127.0.0.1:3003)
         书单数据 / 封面 / 正文 / calibre 自己的阅读器 SPA / 格式转换

两个数据库:
  calibre 的 metadata.db   只读(经 HTTP 访问,不直连)
  data/reading.db          可写(SQLite + WAL),关联键 = calibre 的 books.uuid
```

**为什么要让 Node 转发,而不是前端直连 calibre**

查过 calibre 的 `src/calibre/srv/` 全目录:`Access-Control-Allow-Origin` 与 `cors`
**零命中** —— 它不返回任何 CORS 头。浏览器跨端口 `fetch` 会被拦,所以必须同源;
而 calibre 自己占着 `/`(它的 `index()` 返回自家 SPA,`srv/code.py:38`),
只能挂子路径。Node 转发顺带解决了另外三件事:统一契约、双库 join、流式转发大文件。

## 二、为什么关联键必须是 UUID

calibre 每本书有三个可用标识,只有 UUID 稳定:

| 标识 | 为什么不稳 |
|---|---|
| `books.id` | 删了再加会变 |
| `books.path`(`Author/Title (id)`) | 改书名/作者会重算(calibre `db/cache.py` 的 `update_path`) |
| **`books.uuid`** | **稳定**,且 calibre 插入时由触发器自动生成(`resources/metadata_sqlite.sql:371`) |

calibre 的 `/ajax/books?ids=<uuid>&id_is_uuid=true` 原生支持按 uuid 查
(`srv/ajax.py:205` 的 `lookup_by_uuid`),所以这条关联是官方支持的用法。

> ⚠️ 实现细节:取单本时**不要**用 `/ajax/book/{uuid}` —— 它的 `book_to_json`
> 会把 `db_id` 从响应里 pop 掉(`srv/ajax.py:67`),拿不到数字 id,而封面/正文
> URL 需要数字 id。改用 `/ajax/books?ids=<uuid>&id_is_uuid=true`,它返回
> `{数字id: {...}}` 字典,一次同时拿到数字 id 与元数据。

## 三、calibre 的三个关键配置(缺一不可)

```bash
calibre-server \
  --listen-on 127.0.0.1 \      # 只监听本机,由 Nginx/Node 反代
  --port 3003 \                # 3001=ecook,3002=my-books,故用 3003
  --url-prefix /calibre \      # 必须挂子路径,把 / 让给新前端
  --trusted-ips 127.0.0.1 \    # 写操作只信任本机(Node)
  /root/calibre-library
```

**① 绝不要加 `--enable-auth`**

calibre 的 `/ajax/*` 端点 `auth_required` **默认为 True**(`srv/routes.py:116`),
平时匿名能浏览只是因为没开 auth 时 `auth_controller` 为 `None`
(`srv/handler.py:202`),`routes.py:362` 直接跳过校验。一旦开启认证,
**连 `/get/cover` 封面图都要登录**,公开站点直接废掉。

这就是为什么「读公开 + 写走 trusted-ips」是唯一可行组合。

**② `--url-prefix` 必须配 Nginx 尾斜杠 301**

calibre 官方手册(`manual/server.rst:324-327`)对 nginx 明确要求
`rewrite /calibre /calibre/ permanent`,否则相对路径与 Service Worker 会错位。
`deploy/nginx-helloac.top.conf` 里已加:

```nginx
location = /calibre { return 301 /calibre/; }
```

**③ 不要直连 `metadata.db`**

两个原因,都会实际报错:

1. calibre 的 schema 依赖它用 apsw 注册的 Python 函数(`db/backend.py:424-432`):
   `title_sort`、`uuid4`、`author_to_author_sort`、`books_list_filter`,
   还有 collation `PYNOCASE`/`icucollate`。读它的**视图**(如
   `tag_browser_ratings`,schema 里带 `books_list_filter(book)`)会直接报
   `no such function`。
2. **绝不能往 `metadata.db` 写** —— 写入会触发 `books_insert_trg` 调
   `title_sort()`,我们这边没有该函数。

另外 calibre **不用 WAL**(全 `src/calibre/` 搜 `journal_mode` 零命中),
它靠 `busy_timeout=10000` 串行化,走 HTTP 让 calibre 自己管连接最干净。

## 三之二、四条实测踩过的坑(2026-10-09 上线实录)

这一节是血泪记录,重装时**照做可避免重复排查**。

### 坑 1:缺 `libGLX.so.0` → 服务崩溃重启,报错却指向 QBrush

现象:`systemctl status` 显示 `activating (auto-restart)`,exit code 1,
日志里是:

```
Failed to import PyQt module: PyQt6.QtGui with error:
  libGLX.so.0: cannot open shared object file
ImportError: cannot import name 'QBrush' from 'qt.core'
  at calibre/ebooks/covers.py:13
```

**根因链**:`libGLX.so.0` 缺失 → `PyQt6.QtGui` 加载失败 →
calibre 的惰性加载器取不到 `QBrush` → `covers.py:13` 的模块级 import 崩 →
`srv/content.py` → `srv/ajax.py` → `Handler` 构造抛异常 → 服务退出。

**坑点**:官方安装脚本**自己不检查 libGLX**。它只查
`libEGL`/`libOpenGL`/`libxcb-cursor`/freetype(`linux-installer.sh:800-889`),
所以你按它的提示装完 `libegl1 libopengl0 libxcb-cursor0` 仍然起不来,
而报错文案是 `QBrush` —— 很难联想到"缺 GL 库"。

**解法**:

```bash
apt-get install -y libglx0 libgl1 libglvnd0
```

`deploy/setup-calibre.sh` 已内置这组依赖的安装与验证。
一次性查全所有缺失库的办法:

```bash
ldd /opt/calibre/lib/calibre-extensions/*.so 2>/dev/null | grep -i "not found" | sort -u
```

### 坑 2:库目录为空时启动 → 无休止崩溃重启

`calibre-server` 启动时硬检查 `metadata.db`:

```python
# calibre srv/standalone.py:215-217
for lib in libraries:
    if not lib or not LibraryDatabase.exists_at(lib):
        raise SystemExit(_('There is no calibre library at: %s') % lib)
# db/legacy.py:266-268
@classmethod
def exists_at(cls, path):
    return path and os.path.exists(os.path.join(path, 'metadata.db'))
```

而 `metadata.db` 要由第一次 `calibredb add` 创建 —— 典型鸡生蛋。
若在此状态下 `systemctl enable --now`,systemd 会无限重启它。

**解法**:先导入书建库,再启动服务。`setup-calibre.sh` 已改为
「只 enable 不 now,库存在才启动」。

### 坑 3:`calibredb` 与 `calibre-server` 抢同一把全局锁,不能同时跑

```python
# calibre-server 启动时:srv/standalone.py:177-186
def ensure_single_instance():
    if not singleinstance('db'):
        raise SystemExit('Another calibre program ... is running')

# calibredb 启动时:db/cli/main.py DBCtx
if not singleinstance('db'):
    raise SystemExit('Another calibre program such as calibre-server ... is running')
```

**同一把 `db` 文件锁**。所以任何 `calibredb` 操作前都要先停服务:

```bash
systemctl stop calibre-server
# …跑 calibredb / import-to-calibre.js…
systemctl start calibre-server
```

**或者**让 calibredb 通过 HTTP 连运行中的服务(无需停服务):

```bash
calibredb --with-library 'http://127.0.0.1:3003/calibre/#calibre-library' list
```

### 坑 4:`import-to-calibre.js` 重跑会重复导入

calibre 的 `add_books` 默认 `add_duplicates=True`(`db/cache.py:2683`),
所以重跑一次脚本会把每本书再加一遍 —— 实测得到 **26 本 = 13 本 × 2 份**,
紧接着让阅读记录迁移**每本都报"有 2 个候选"的歧义**。

**解法**:脚本现已默认查重(按书名+作者指纹跳过已存在的),
要建重复记录需显式加 `--allow-duplicates`。

## 四、部署步骤

### 1. 装 calibre 后端

```bash
cd /root/my-books
bash deploy/setup-calibre.sh
```

脚本会:装官方二进制 → 建库目录 → 装 systemd 服务 → 启动 → 自检。

> ⚠️ **仓库里的 `calibre-master/` 跑不起来** —— 它是纯源码,`calibre_extensions`
> 的 C/C++ 扩展没有编译产物(`stubs/calibre_extensions/` 下只有 `.pyi` 类型存根)。
> 必须装官方二进制。

### 2. 放书进去

```bash
# 命令行
calibredb add /path/to/*.epub --library-path /root/calibre-library

# 或者在本地 calibre GUI 里管理,再把库目录同步上来
```

### 3. 配 Nginx

```bash
sudo cp deploy/nginx-helloac.top.conf /etc/nginx/conf.d/helloac.top.conf
sudo nginx -t && sudo systemctl reload nginx
```

### 4. 重启 Node(让它读到新的环境变量)

```bash
pm2 restart my-books --update-env
```

`deploy/ecosystem.config.js` 里已加:

```js
CALIBRE_URL: 'http://127.0.0.1:3003/calibre',
CALIBRE_TIMEOUT_MS: '10000',
CALIBRE_SLOW_TIMEOUT_MS: '60000',
OPEN_ACCESS: '1',          // 读写全公开
```

> `OPEN_ACCESS=1` 会关闭应用层 Bearer token 鉴权。不设或设 `0` 时,
> POST/PUT/DELETE 仍要求 token(默认 fail-closed,`test/auth.test.js` 依赖此行为)。

### 5. 打开新前端

```
https://helloac.top/next/
```

### 6. 迁移旧阅读记录

```bash
cd /root/my-books
node deploy/migrate-reading.js --dry-run   # 先看匹配结果
node deploy/migrate-reading.js             # 确认后执行
```

脚本按 ISBN → 书名+作者 → 书名 三级回退匹配 calibre 里的书,
**匹配不上的会全部列出来**,不会静默丢弃。

## 六、阅读器的位置(重要)

**calibre 的阅读器不能嵌进新前端,只能跳转过去。**

原因:calibre 的阅读器与书单是**同一份编译产物的同一个 SPA**。
`src/pyj/srv.pyj` 是唯一入口,它同时 import 两者;编译产物是单个
`resources/content-server/index-generated.html`(`utils/rapydscript.py:692` 的
`compile_srv()` 注入 reset.css + icons + base.css + 全部 JS)。它靠
`#mode=read_book` 这个 URL hash 在同一个 SPA 内切换模式
(`book_list/router.pyj:41,102-118`),并且耦合了 calibre 自己的后端会话
(IndexedDB 四个 store、`ajax-setup`、`library_data`)。

所以路径是:

```
新前端书单 ──点「在 calibre 中阅读」──► /calibre/#book_id=123&fmt=epub&mode=read_book
```

**进度同步:按你的决定,放弃跨设备同步。**

这不是缺陷,而是 calibre 在未登录状态下的原生降级路径 ——
阅读进度存在浏览器 IndexedDB 里(`read_book/db.pyj`),换设备不同步。
根本原因是 calibre 的进度接口要求登录(`srv/books.py:215-217`):

```python
user = rd.username or None
if not user:
    raise HTTPNotFound('login required for sync')
```

而开 auth 又会让封面图也要登录(见第三节①),所以这是个死结。
"读书记录"(已读/读了几遍/日期)完全不受影响,因为它在 `reading.db` 里。

## 七、日常运维

```bash
pm2 restart my-books                 # 重启 Node
pm2 logs my-books                    # 看日志
systemctl status calibre-server      # calibre 状态
journalctl -u calibre-server -f      # calibre 日志
bash deploy/update.sh                # 更新代码(会先备份**两个**库)
```

### 备份

`deploy/update.sh` 现在会**分别备份两个库**,且都用 `VACUUM INTO`:

```
data/backup/books-YYYYMMDD-HHMMSS.db
data/backup/reading-YYYYMMDD-HHMMSS.db
```

> **绝不能 `cp data/reading.db`** —— 它在 WAL 模式下,已提交事务可能只在
> `-wal` 文件里。实测 `cp` 主库文件会得到一个"能打开、但缺 80% 数据"的备份,
> 而且 `PRAGMA integrity_check` 依然报 `ok`,校验抓不出来。
> `deploy/backup-db.js` 用 `VACUUM INTO` 并比对**所有用户表**的行数。

### 排查速查

| 现象 | 处理 |
|---|---|
| 页面提示「calibre 后端不可用」 | `systemctl status calibre-server`;确认 `--port` 与 `CALIBRE_URL` 一致 |
| 打开 `/calibre` 白屏 / 资源 404 | Nginx 的 `location = /calibre { return 301 /calibre/; }` 丢了 |
| 封面全是占位色块 | calibre 里该书没有封面;或 `/api/calibre/cover/:id` 转发失败 |
| 书单是空的但 calibre 里有书 | 确认 `--url-prefix /calibre` 生效:`curl 127.0.0.1:3003/calibre/ajax/library-info` |
| 写阅读记录 401 | `OPEN_ACCESS` 未设为 `1`,且没带 token |
| 重复的书 / 状态对不上 | 关联键是 uuid;检查 calibre 里是否有同书名的多条记录 |

## 八、安全:两条必须知道的边界

### ① `/calibre/cdb/` 必须拦住(已在 Nginx 配置里)

calibre 的写权限判定是 `is_trusted_ip`(`srv/loop.py:179-181`、
`srv/handler.py:120-126`),而 `--trusted-ips 127.0.0.1` 本意是
"只信任本机"。**但经 Nginx 反代后,所有公网请求的源地址都变成
127.0.0.1** —— calibre 于是认为每个访客都可信。

后果:任何人执行

```bash
curl https://helloac.top/calibre/cdb/delete-books/1
```

就能删掉 id=1 的书。

`deploy/nginx-helloac.top.conf` 已内置拦截:

```nginx
location /calibre/cdb/ { return 403; }
```

我们的架构本就不需要 calibre 的写接口(书由 `calibredb`/GUI 管,
阅读记录走 `/api/reading/*`),所以整体拒绝。

### ② `/api/reading/*` 当前全天候开放写

`OPEN_ACCESS=1`(见 `deploy/ecosystem.config.js`)会关闭应用层 Bearer
鉴权,读写全部公开。这是按需求刻意设置的,但要清楚它的含义:
**任何人都能改你的阅读记录**(想读/在读/已读、读过几遍)。

若要收紧,两条路:
- 去掉 `OPEN_ACCESS`(恢复默认的 fail-closed:写操作需 `ADMIN_TOKEN`)
- 或在 Nginx 层对 `/api/reading/` 的非 GET 方法加 IP 白名单

## 九、已知取舍

| 取舍 | 说明 |
|---|---|
| 进度不跨设备 | calibre 阅读器的原生行为(见第六节);要同步就必须登录,而登录会让公开浏览失效 |
| 搜索中文可能变弱 | calibre 的 FTS 用 `unicode61`;项目原有的 `search.js`(FTS5 **trigram**,中文子串友好)仍可用作补充 |
| 标签分布需扫全库 | `/api/calibre/stats` 会 `ids=all` 拉全量元数据。个人库量级没问题;库很大时应改为定时预聚合 |
| 无实时变更推送 | calibre 没有 `/changes` 端点(查过),WebSocket 也不广播数据变更。前端是拉取式 |
| 网站不能加书 | 书由 calibre GUI / `calibredb` 添加(方案 A)。Node 的写能力是为阅读记录准备的 |
